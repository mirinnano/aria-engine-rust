# 仕様の練り直し

2026-10-22。
現行の仕様（`docs/spec/`）と実装、および唯一の作品 HesPhoros の使い方を照らし合わせ、各部分を「残す」「変える」「捨てる」に分けた。
判断の基準は三つである。
作品が実際に使っているか。
使っていないなら、使う見込みが具体的にあり、かつ保守の費用に見合うか。
仕様どうし、または仕様と実装が矛盾していないか。
批評の記録は `../reviews/aria-engine-skeptic.md`（作業フォルダの `reviews/`）にある。

この文書は提案であり、`docs/spec/` はまだ書き換えていない。
各節の判断が通ったら、仕様を先に書き換え、実装をそれに合わせる。

---

## 1. Native をどう作るか

### 現状

`aria-native`（Winit、wgpu、Kira）は、背景、表示資源、プラグインの描画層だけを描く。
本文、選択肢、メニューを描くコードは `aria-native` にも `aria-render` にもない。
`aria build --target windows-x64` はこのプレイヤーと PAK をまとめるので、出来上がったゲームでは物語が読めない。
HesPhoros は、このために Tauri の殻を自前で作り、WebView の中で `aria-web` の Wasm と React の表示パッケージを動かしている。
つまり現在の「デスクトップ版」は、Web 版をウィンドウに入れたものであり、VM は Wasm として動いている。

### 選択肢

**A. wgpu のプレイヤーに UI を足す。**
`presentation.md` は、レイアウト、字体、配色、操作を表示パッケージ（React など）の受け持ちとしている。
wgpu で UI を描くと、作品ごとに React 版とは別の UI をもう一つ書くことになり、この分担と矛盾する。
採らない。

**B. 現状どおり、WebView の中で Wasm の VM を動かす。**
動くことは HesPhoros で確かめられている。
しかし VM、PAK、保存のすべてが Wasm の中にあり、Native の利点（素材をファイルから必要な分だけ読む、OS の保存先に直接書く、ストアの機能を Rust から呼ぶ）を得られない。
Wasm の線形メモリに PAK を丸ごと置くので、素材が増えるほどメモリを使う。
「Native と Web の一致」も、同じ Wasm を二か所で動かすだけになり、確かめる意味がない。

**C. VM を Rust のネイティブコードとして動かし、WebView には表示パッケージだけを置く。**
デスクトップでは、VM、PAK、保存、プラグインを Rust のプロセスが持ち、WebView の表示パッケージとは IPC でやりとりする。
Web では、同じ役割を Wasm が受け持つ。
表示パッケージから見ると、相手が Wasm か IPC かの違いしかない。

### 判断：C を採る

C だけが、表示パッケージを一つに保ったまま、Native を名前どおりの Native にできる。
表示パッケージと VM の間の約束（ホストのインターフェース）を一つ定め、それを Wasm と IPC の二通りに実装する。
エンジンは、いま HesPhoros にある Tauri の殻を引き取り、`aria-desktop` として持つ。
`aria build --target windows-x64` は、`aria-desktop` と表示パッケージと PAK をまとめ、そのまま読めるゲームを出す。

この判断に伴って、次のものを捨てる。

| 捨てるもの | 理由 |
|---|---|
| `aria-native` の Winit、wgpu、Gilrs、AccessKit の部分 | 物語を表示できず、C では使わない。ゲームパッドとアクセシビリティは WebView の Gamepad API と DOM が受け持つ |
| `aria-render` | 描画は表示パッケージだけが行う |
| `aria-native` の Kira の部分 | 音は表示パッケージの Web Audio で鳴らす。デスクトップと Web で同じ音の処理を使える |

`ReplayRunner`（入力記録の再生）と画面なしの実行は、描画に依存しないので `aria-cli` に移して残す。

### C の危険と、確かめてから進むこと

現在の表示パッケージは、タイプライタの表示中に毎フレーム VM の `step` を呼び、表示モデルの JSON を受け取っている。
これを IPC に置き換えると、毎秒 60 回の往復と JSON の変換が発生する。
そこで、タイプライタの進行を表示パッケージの受け持ちに移す（3 節の「時間の受け持ち」）。
そうすれば `step` が呼ばれるのは入力とタイマーのときだけになる。
それでも、Windows（WebView2）、macOS（WKWebView）、Linux（WebKitGTK）で、入力から画面が変わるまでの遅れを測ってから移行する。
遅れが 1 フレーム（16ms）を超える環境があれば、その環境だけ B に戻せるよう、ホストのインターフェースは B の実装も残す。

### 対象とする環境：家庭用ゲーム機は当面外す

（2026-10-24 決定）エンジンが対象とするのは、デスクトップ（Windows、macOS、Linux）、Web、のちのスマートフォンである。
Nintendo Switch や PlayStation などの家庭用ゲーム機は、HesPhoros が売れて開発の資金ができるまで対象にしない。

C は画面を WebView に任せる設計であり、家庭用ゲーム機ではゲームが WebView を使えない前提で考えるべきである。
したがって、家庭用ゲーム機に出すには、画面を描く仕組みをネイティブで別に持つ必要がある。
その道は二つ考えられる。
一つは、商業のノベルエンジン（Artemis Engine など）のように、画面を画像のレイヤーの組み合わせで描く方式である。
もう一つは、家庭用ゲーム機に対応した HTML/CSS の UI 製品（Coherent Labs の Gameface など）を組み込む方式である。
どちらも、いまの表示パッケージ（React と CSS）を作り直すか、有料の製品と契約するかになり、作品の収益がない段階で負える費用ではない。
一方で、HesPhoros の画面の質は、CSS で背景のぼかし、グラデーション、影、アニメーション、ルビを短く書けることに支えられている。
家庭用ゲーム機のためにこれを今手放すと、作品を出すのが遅れ、見た目も落ちる。

この判断から、次の二つを守る。

- 表示モデルは、描画の方法に依存しない意味の値だけを持つ（3 節「VM が持つ描画命令をやめる」）。家庭用ゲーム機向けの描画を後から作るとき、台本、VM、保存はそのまま使い、表示の側だけを足せるようにするためである。
- 将来の家庭用ゲーム機向けの描画は、そのときの選択肢から選び直す。上の表で捨てる `aria-native` の wgpu の部分と `aria-render` は、本文もメニューも描けないので、その土台としては残さない。必要になれば、履歴から取り出せる。

## 2. 台本の言語

### 残すもの

次のものは作品が使っていて、仕様と実装が一致しているので、そのまま残す。

- `scene`、`entry`、`jump`、`choice`（`if` と `cancel` を含む）、`end`、`use`
- `narrate`、`say`、`await advance`、`wait`、`wait breath`
- `prose`（`+` は後述のとおり意味を直す）
- 文中の記法（ルビ、傍点、`{wait:…}`、`{変数}`）
- `character`、`chapter`、`collection`、`cg` の宣言
- `flag`、`persistent flag`、`state`（`Int`、`Bool`、`String`）、`if`、`call`、`while`
- `stage`、`camera`、`play`／`stop`（`bgm`、`ambient`、効果音、声）、`background`

`call` と `while` は作品で使っていないが、実装が小さく、ほかの機能と干渉しないので残す。

### 変える：`prose` の `+`

仕様は `+` を「本文を消さずに次の行へ続ける印」としているが、実装では次の行が本文を置き換える。
HesPhoros は仕様を信じて `+` を使っており、一文が二画面に分かれている。
仕様の意味のほうを正とし、実装を直す。

新しい意味は次のとおりである。
`+` でつないだ行の並びを一つのページとする。
各行の後で読者の入力を待ち、次の行は同じページの後ろに追記する。
ページの最後の行（`+` のない行）の後で、ページを消して間を置く。
バックログにはページを一つの項目として残し、既読と再開の位置は行ごとに数える。
VM の本文の命令に「追記する」の区別を加える。

（2026-10-22、実装時の判断）表示モデルの `dialogue` は形を変えず、追記した分だけ本文が伸びるようにした。表示パッケージを直さずに済むからである。
HesPhoros は `prose` の最後の行の `+` を「本文を残し、間を置かずに `prose` を抜ける」意味で 5 か所使っていたので、これを仕様として認めた。
また、台本の `text_speed` が読者の設定を書き換えていたため、システムデータを起動時に戻すと読者の選んだ速さが毎回上書きされることが分かった。`text_speed` は作品の既定の速さとし、読者が選んだ速さを優先する。

### 変える：表示資源の所有権をやめ、名前の付いた枠にする

現行の仕様では、`show` で作った表示資源を所有権と借用で管理し、座標をピクセルで書く（`at (760px, 86px)`）。
これには二つの問題がある。

第一に、`presentation.md` は「台本に座標を書かない」と定めており、`aria.md` の例がそれに反している。
座標を台本に書くと、表示パッケージが画面の大きさや配置を変えたときに台本も直すことになる。

第二に、所有権と借用は、作品が一度も使っていないのに、コンパイラの最も大きな部分を占めている。
ノベルの作者が表示資源について知りたいのは「誰がどこに出ているか」であり、所有権の移動や可変の借用ではない。

そこで、表示資源を、名前の付いた枠と意味としての位置で表す。

```aria
show mio asset("assets/portrait/mio-smile.webp") at left;
show mio asset("assets/portrait/mio-quiet.webp");   // 同じ枠の絵を替える
move mio to center;
hide mio;
```

位置の名前（`left`、`center`、`right` など）は `stage` と同じく意味だけを表し、座標は表示パッケージが決める。
`aria.toml` の `[presentation] positions = [...]` に表示パッケージが扱う名前を並べると、`aria check` はそれ以外をエラーにする。
コンパイラは、出ていない枠への `move` と `hide` をエラーにし、場面の終わりで枠が残っていることを警告する。
所有権が防いでいた誤り（消した資源を動かす、二重に消す）は、この検査で同じように防げる。

### 変える：独自画面を台本で宣言する

HesPhoros のプラグインは、独自画面三つ（`day_card`、`interlude`、`statement`）の入力方針を宣言するためだけにある。
方針はデータであり、Wasm のコードも署名も要らない。
画面の宣言を台本に移す。

```aria
screen interlude {
    reading;
    atomic_text;
    playback_controls;
    advance_releases_hold;
    skip_releases_hold;
    advance_action "interlude.advance";
    auto_hold_cap 320ms;
    first_visit_min_hold 600ms;
}
```

項目は現行の `RoutePolicy` と同じである。
標準の画面名を上書きできないこと、名前が重なれば拒否することも、現行の規則を引き継ぐ。

### 変える：画面ごとに、出せるものを決める

HesPhoros の表示パッケージは、「画面が `chapter_select` で、本文があり、選択肢が空なら日付カード」と、表示モデルの形から画面の意味を推し量っている。
これは、`presentation.md` が禁じた推定と同じ種類の脆さを持つ。
推定が要るのは、一つの画面が本文と一覧の二つの状態を持てるからである。

そこで、本文を出せるのは `reading` の画面だけとし、`chapter_select` や `gallery` のような一覧の画面で `narrate` や `say` を書くとコンパイルエラーにする。
日付カードのように本文を出してから一覧へ移る流れは、`screen day_card;` で本文を出し、そのあと `screen chapter_select;` に移ると書く。
表示パッケージは画面名だけで描き方を決められる。

## 3. VM

### 残すもの

- Core が窓、GPU、音、時計、ファイルを持たず、時刻と入力をホストから受け取る分担
- レジスタを名前で引くこと。改稿で変数の並びが変わっても、保存した値を名前で戻せる
- 呼び出しの深さの上限、プログラムの検証、ARIAC のチェックサム

### 変える：実行時の型を厳密にする

コンパイラは型を検査するのに、VM は浮動小数点を切り捨て、文字列を数として読み、値がなければ 0 を返し、知らない比較演算子には `false` を返す。
コンパイラの外から入る値（保存、改稿後の再開、古い ARIAC）に誤りがあると、これらの変換が誤りを隠す。
VM は型の合わない値と知らない名前をすべてエラーにする。
比較演算子、遷移、イージング、画面効果の種類は、文字列ではなく列挙の番号として命令に入れ、コンパイラだけが名前を解決する。
未設定の変数は、`state` の初期値をプログラムの表として持ち、読み込み時に埋める。

### 変える：浮動小数点を VM から外す

VM は、音量、トゥイーン、イージングの計算に `f32` を使っている。
四則演算は Native と Wasm で同じ結果になるが、`powi` などの関数は環境ごとに結果が変わりうる。
また、途中の値を VM が計算する必要はない。
カメラについては、すでに「VM は目標と時間だけを持ち、表示パッケージがそこへ向かって動かす」と定めている。
同じ扱いを、表示資源の移動、画面効果、音量の変化に広げる。
VM が持つ値は、整数（ミリ秒、千分率、百分率）と名前だけにする。

### 変える：時間の受け持ち

タイプライタの速さは読者の設定であり、`presentation.md` の規則では表示パッケージが決めてよい時間である。
現行の VM はタイプライタの進み具合を毎フレーム計算しているので、表示パッケージが毎フレーム `step` を呼ぶ必要がある。
タイプライタは表示パッケージに移し、VM は「この行を出した」「読者の入力を待っている」だけを持つ。
文中の `{wait:300}` は台本が決めた時間なので、表示パッケージはタイプライタの途中でその時間だけ止まる（値は表示モデルの記法の範囲で渡る）。
画面の幅から字幕の列数を決めてページを分ける処理（`subtitle_columns`）も、表示の判断なので表示パッケージに移す。
VM が数えるページは、2 節の `+` でつないだ、作者が決めたページだけになる。
オートの待ち時間は、本文の長さと設定から VM が計算する（オートで進むかどうかは物語の進行に関わるため）。
この変更は 1 節の IPC の頻度を下げる前提でもある。

### 変える：宣言を命令列から出す

章、資料、CG の宣言は、現在 `DeclareChapter` などの命令として命令列に入っている。
これらは実行されない資料なので、ARIAC に資料の表を設けてそこに置く。
`state` の初期値と型、独自画面の宣言、行のキーも同じ表に置く。

### 変える：VM が持つ描画命令をやめる

VM は表示モデル（`UiViewModel`）とは別に、描画命令の列（`scene`）を出している。
1 節の判断で描画は表示パッケージだけが行うので、描画命令の列は二つ目の約束になる。
背景、`stage`、カメラ、表示資源の枠は、意味としての値で表示モデルに入れ、描画命令の列は廃止する。

## 4. 保存

### 変える：周回をまたぐデータを、保存枠から分ける

現行の実装では、一つの保存枠に、物語の位置と状態に加えて、周回フラグ、既読、章と CG の解放、設定がすべて入る。
保存を読み込むと、VM の状態が保存の中身で丸ごと置き換わる（`Vm::restore` の `self.state = snapshot`）。
そのため、古い保存を読み込むと、その後に立てた周回フラグ、読んだ行の既読、解放した CG、変えた設定が、保存した時点に戻る。
`persistent flag` の「周回をまたいで残る」という仕様が、保存を読み込んだ時点で成り立たなくなる。

データを二つに分ける。

| 種類 | 中身 | 保存のされ方 |
|---|---|---|
| システムデータ | 周回フラグ、既読の行、章と CG の解放、設定 | 作品ごとに一つ。読み込みで置き換えず、和集合で増えるだけ |
| 保存枠 | 位置、呼び出しスタック、周回内のフラグと変数、背景や枠の状態、選択の記録 | 枠ごと |

### 変える：改稿後の再開は、選択の記録を再生して行う

現行の実装は、改稿後に再開するとき、位置だけを新しい台本に移し、変数とフラグは古い台本で作った値をそのまま使う。
改稿で保存位置より手前にフラグの命令を足すと、その効果が再開後の状態に入らない。

一方で、VM にはすでに、選択の記録に沿って最初から実行し直す仕組みがある（バックログから戻る操作）。
これを再開にも使う。

1. 保存したときと同じ台本なら、保存した状態をそのまま戻す（いまと同じ）。
2. 台本が変わっていれば、新しい台本を最初から実行し、保存の選択の記録どおりに選び、保存した行に着いたところで止める。状態は新しい台本で作り直されたものになる。
3. 記録した選択肢が新しい台本で見つからない、または保存した行に着かない場合は、現行の位置の付け替えに戻し、読者に「改稿のため、再開の位置がずれた可能性がある」と知らせる。

再生にかかる時間は物語の長さに比例する。
HesPhoros の規模（約 5,000 行）で測り、許容できなければ章の先頭ごとに中間の状態を記録して、そこから再生する。

### 変える：行の同一性

行のキーは、場面名と、話者と本文のハッシュから作り、同じ文が続くと出現順の番号を付けている。
「……」のような同じ文を一つ手前に足すと、後ろの番号がすべてずれ、既読と再開の位置が別の行に移る。
キーに直前の行のハッシュを含め、同じ文でも前の行が違えば別のキーにする。
それでも区別できない行には番号を付けるが、`aria check` で警告する。
加えて、`aria check --against <前の版の .ariac>` を設け、改稿で既読や保存の位置が動く行を一覧にする。
HesPhoros は改稿のたびに保存の名前空間を替えて古い保存を捨てている（`save_namespace = "umikaze-v5"`）。
作者自身がいまの付け替えを信用していないことを示しており、この一覧はその判断の材料になる。

### 変える：保存形式の互換の守り方

現在は、保存形式の版を上げるたびに `cross_runtime_determinism` の固定ハッシュを書き換えている。
1.0 からは、各版の保存の実物をテストの資料としてリポジトリに置き、新しい版でそれを読み込めることを確かめる。
読み込めなくする変更は、移行の処理を書くか、版の番号の大きな変更として扱う。

## 5. プラグイン

### 残すもの：`commands`

台本から呼ぶ命令は、要求と状態を受け取って応答を返す純粋な関数であり、決定性と保存の互換を保ちやすい。
4 節の再生による再開でも、同じ要求に同じ応答が返るので問題が起きない。
作品はまだ使っていないが、例（`tally`）があり、言語の拡張の口として残す。
fuel とメモリの上限もそのまま残す。

### 捨てるもの

| 捨てるもの | 理由 |
|---|---|
| `routes` | 2 節で台本の宣言に移す |
| `hooks`（本文、選択肢、場面への進入） | 本文や選択肢をプラグインが書き換えると、台本に書いた行と画面に出る行が一致しなくなり、既読、再開、バックログの前提が崩れる。使う作品もない |
| `render`（描画層）と同梱の `ui.js` | 描画は表示パッケージの受け持ちである。描画層と `ui.js` を残すと、描画の約束が三つになる |
| ユーザーデータのフォルダからの読み込み | 配布後にプラグインだけを差し替える用途が、まだ具体的にない。プラグインはビルドで PAK に入れ、更新は PAK の差分（`overlay`）で配る |

プラグインが PAK の中に入れば、プラグイン単独の署名と `trusted_keys` は要らなくなり、PAK の検証が代わりを務める。

## 6. PAK と保護

### 残すもの

- チャンクごとの圧縮と BLAKE3 のハッシュ、content root
- パッケージの役割（`boot`、`hot`、`cold`、`overlay`）。HesPhoros は `hot` と `cold` を使っている

### 変える：プロファイルを二つにする

| プロファイル | 中身 | 用途 |
|---|---|---|
| `dev` | ハッシュのみ | 手元の開発 |
| `release` | ハッシュ。署名は任意 | 配布物 |

署名は、配布の途中での改ざん（CDN、自動更新、差分の配信）を防ぐためのものと仕様に明記する。
手元の配布物を書き換えられる者は公開鍵も差し替えられるので、署名はそれを防がない。
この脅威が当てはまらない配布（ストア経由の配布など）では、署名を省ける。

### 捨てるもの：`protected` と利用許可（lease）

`LicenseProvider` の実装はテストの中にしかなく、作品も `protected` を使っていない。
Web 版の暗号化は、仕様自身が「手軽な複製を防ぐためのもの」と認めている。
暗号鍵の配布と利用許可のサーバーを持たないまま、暗号化の形式だけを保守する理由がない。
有料の配布で保護が要るようになったら、そのとき配布先（Steam など）の仕組みを使う。

## 7. 決定性の確かめ方

現行の `cross_runtime_determinism` は、同じ VM を二つの薄い包みから同じホストで動かしているので、Native と Web の差を見つけられない。
1 節の判断で、デスクトップの VM はネイティブコード、Web の VM は Wasm になる。
テストは、`wasm32-unknown-unknown` にビルドした VM を Node で動かし、ネイティブの VM と同じ入力記録を与えて、表示モデルと保存のハッシュを比べる。
入力記録は、`examples/` の最小の作品に加え、HesPhoros の台本でも作る（HesPhoros の CI で回す）。
3 節で VM から浮動小数点を外すので、差が出る余地はもともと小さい。
このテストは、それが保たれていることを確かめる役になる。

## 8. 仕様と開発の進め方

### 仕様を正とする

現行の言語仕様は「細部は構文解析とコンパイラで確かめる」と書き、実装に判断を預けている。
そのため、`+` のように仕様と実装が食い違ったとき、どちらを直すかの根拠がない。
仕様を正とし、仕様の各節にその節を確かめるテストの名前を書く。
仕様にない振る舞いは、仕様に書き足すか、実装から消す。

### エンジンの作業場所を一つにする

手元の `aria-engine-rust` と `hesphoros/engine` は、統合済みの別々のブランチを開いたまま `main` から遅れていた（どちらも `origin/main` の `18b085e` に統合されている）。
修正は `aria-engine-rust` で `main` から切ったブランチに入れ、HesPhoros はサブモジュールの参照を進めることでだけ取り込む。

### README の書き換え

README は、捨てるものを載せず、足すものを載せる。

| README の項目 | 扱い |
|---|---|
| 「Native と Web で同じように実行する」 | 残す。7 節のテストで裏付けられるようになる |
| 「構文・型・所有権の面から検査する」 | 「所有権」を外し、「構文、型、画面と位置の名前、制御フロー」に替える |
| `crates/aria-native`（Winit、wgpu、Kira） | 消す。`crates/aria-desktop`（Tauri の殻。VM はネイティブで動き、表示パッケージを WebView で表示する）を足す |
| `crates/aria-render` | 消す |
| `crates/aria-protection`（署名、暗号化、ライセンス） | 「PAK の検証と署名」に縮める |
| `crates/aria-plugin-host` | 残す。説明を「台本から呼ぶ命令の実行」に縮める |
| `ui/packages/aria-ui-sdk` | 残す。ホストのインターフェース（Wasm と IPC の共通の型）を足す |
| `aria run` | 残す。画面ありの実行は `aria-desktop` で行う |
| `aria build` の Windows、macOS、Linux 向け | 残す。出力が、表示パッケージを含む読めるゲームになる |
| `aria check --against` | 足す |

## 9. 進める順序

作品への影響が大きく、他の変更の前提になるものから進める。

1. `aria-engine-rust` を `main` の最新に合わせ、作業用のブランチを切る。
2. `+` の意味を直す。システムデータを保存枠から分ける。どちらも、いま作品に出ている不具合である。
3. 独自画面を台本の宣言に移し、画面ごとに出せるものを決める。HesPhoros のプラグインと、表示パッケージの推定を消す。
4. タイプライタを表示パッケージに移す。そのうえで `aria-desktop` の試作を作り、三つの OS で IPC の遅れを測る。
5. 遅れが許容範囲なら、`aria-desktop` を本番にし、`aria-native` の描画と音、`aria-render`、描画命令の列、`protected` と lease、プラグインの `hooks` と `render` を消す。
6. VM の型を厳密にし、浮動小数点を外し、宣言を表に移す。表示資源を名前の付いた枠にする。ここで ARIAC と保存形式の版を一度だけ上げる。
7. 再生による再開、行のキーの変更、`aria check --against` を入れる。
8. Wasm とネイティブを比べる決定性のテストに置き換え、HesPhoros の CI でも回す。

1 から 3 は、ほかの判断と独立に進められる。
4 の測定の結果によっては、1 節の判断（C）を見直す。
